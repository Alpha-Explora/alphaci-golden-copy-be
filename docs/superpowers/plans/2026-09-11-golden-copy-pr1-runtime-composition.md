> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax (`- [ ]`) for tracking.

**Goal:** Move the 29-key capability catalog into the backend technical kernel, add declared SaaS/EDU/Enterprise manifests, and implement a pure configuration-and-dependency resolver without wiring any consumer to it yet.

**Status:** Completed locally on `codex/golden-copy-trunk`; checkpoint commits are
local only and no remote push or pull request was created.

**Architecture:** Capability records become application-owned TypeScript data under src/kernel/composition. Edition applicability is declared once in three ordered manifests; the registry describes capability behavior, while the manifests describe pack membership. The resolver narrows a manifest by configuration and the transitive requires closure, returns only executable capabilities, and has no Nest, Billing, persistence, tenant lookup, or edition-comparison branch.

**Tech Stack:** TypeScript 5.7, Node.js CommonJS gate scripts, ts-node/register/transpile-only for the existing TypeScript source loader, Jest with ts-jest, NestJS configuration types, and the repository Node-based documentation gates.

**Spec:** docs/superpowers/specs/2026-09-11-golden-copy-composition-design.md

  readonly edition: Edition;
  readonly capabilities: readonly CapabilityKey[];

  readonly registry?: readonly CapabilityRecord[];
  readonly manifest: CapabilityManifest;
  readonly config: AppConfig;
}

The pure function in PR 1 is deliberately separate from CapabilityResolverPort:

~~~ts
export function resolveCapabilities(
  input: ResolveCapabilitiesInput,
): CapabilitySet;
~~~

The registry no longer carries an editions field. Keeping edition membership in both every record and every manifest would create two mutable declarations of the same fact. The generated matrix derives its edition column by reverse-projecting the three manifests, and the capability gate verifies every manifest key against the registry. This keeps the current tables identical while giving the executable pack declaration one owner.

- [ ] **Step 3: Implement validation and flag lookup.**

Implement resolveCapabilities with these rules:

1. Select input.registry or CAPABILITIES and build a key map. Reject duplicate keys before evaluating a manifest.
2. Validate every manifest key exists, appears once, and occurs in the same order as the registry. A manifest may omit registry records that are not applicable to that edition.
3. Validate every requires key exists and detect cycles with a tri-color depth-first walk. Reject a cycle before resolution so a malformed graph cannot silently resolve to an empty set.
4. Start with only manifest records whose maturity is not-implemented excluded and whose configurationFlags.every(flag => readBooleanPath(config, flag)) is true. readBooleanPath splits a dot path, walks the object, and returns true only when the leaf is exactly true; missing and non-boolean values narrow the set.
5. Repeatedly remove any active record whose requires key is not active. This fixed point is the transitive closure and handles direct and indirect dependencies without edition logic.
6. Return a new Set in registry order. Do not mutate the registry, manifest, config, or a caller-provided set.

The core shape should remain small and explicit:

~~~ts
export function resolveCapabilities({
  registry = CAPABILITIES,
  manifest,
  config,
}: ResolveCapabilitiesInput): CapabilitySet {
  const recordsByKey = validateRegistryAndManifest(registry, manifest);
  const active = new Set<CapabilityKey>();

  for (const key of manifest.capabilities) {
    const record = recordsByKey.get(key);
    if (
      record &&
      record.maturity !== 'not-implemented' &&
      record.configurationFlags.every((flag) => readBooleanPath(config, flag))
    ) {
      active.add(key);
    }
  }

  let changed = true;
  while (changed) {
    changed = false;
    for (const key of [...active]) {
      const record = recordsByKey.get(key);
      if (record && record.requires.some((dependency) => !active.has(dependency as CapabilityKey))) {
        active.delete(key);
        changed = true;
      }
    }
  }

  return new Set(
    registry
      .filter(({ key }) => active.has(key as CapabilityKey))
      .map(({ key }) => key as CapabilityKey),
  );
}
~~~

The committed code must replace the casts in the sample with type-safe helpers where TypeScript can infer them; the sample specifies the algorithm and ordering, not permission to weaken the public type.
