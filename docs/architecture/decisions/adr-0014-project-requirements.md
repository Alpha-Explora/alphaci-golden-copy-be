# ADR-0014: Project requirements

**Decision date:** 2026-10-01
**Decision status:** Accepted
**Supersedes:** the checklist-sharing, per-repository run, per-repository gate and persona-per-item parts of [ADR-0013](adr-0013-qa-verification-runs.md). Its commit-keyed snapshots, server-resolved commits, run-row locking, frozen sign-off report and automated-results rules still stand and are reused unchanged.
**Scope:** Project-owned requirements, the Progress and Verification tracks, Project-scope runs, and the per-Project merge-to-main gate

Terminology: a "Project" is a hierarchy delivery project (the folder that owns repositories); a "repository" is a `projects.provisioned_projects` row.

## Decision

1. **A Project owns its requirements.** They are `projects.qa_checklists` rows with a `delivery_project_id` (a plain UUID, no foreign key: another context owns the Project) and a `kind`: `functional` is a Feature whose items are User stories, `system` is a flat checklist. Every existing checklist becomes a `system` requirement. Product owners (`lead`) and admins create and edit them; nobody else does. Requirements apply to every repository of the Project; the per-repository share table is legacy and no longer read for requirements that have a Project.
2. **Two independent tracks per item.** *Progress* (`todo`, `in_progress`, `done`) lives on the requirement item, set by developers, leads and admins; `done` means ready for QA. *Verification* (`pending`, `passed`, `failed`, `blocked`, `returned_to_dev`) lives on the run item, set by QA, leads and admins. QA never writes Progress and developers never write Verification. Progress is on the definition because it persists across runs; Verification is on the run item because it is a verdict about specific commits.
3. **The tracks meet in three places.** `passed` is refused (409 `QA_PROGRESS_NOT_DONE`) unless the source item's Progress is `done`, checked inside the item write under a `FOR SHARE` lock. `returned_to_dev` sets the source item back to `in_progress` in the same transaction. A developer setting Progress to `done` re-queues any `returned_to_dev` run item to `pending` and notifies QA. Lock order is run row, then run item, then requirement item; a Progress write only takes the requirement item.
4. **QA verifies once per Project.** A Project run captures the `uat` head of every repository when it starts (`qa_run_repositories`) and snapshots every active requirement's items. The key is a sha256 of the sorted `<repository>:<head>` lines, unique per Project, so creating a run for heads that already have one returns it. The server reads the heads; the client never sends a SHA. Repository-scope runs are read-only history; every write on them answers 409 `QA_RUN_LEGACY_READONLY`.
5. **The merge-to-main gate is per Project.** A repository may merge `uat` to `main` only when the latest signed-off Project run (greatest active `signed_at`; open runs never count) is `APPROVED`, the Project has requirements, every head was readable, and the run is current: it covers every repository and each captured head equals the head now. Any repository moving, or joining the Project, makes it stale for all of them. A repository filed under no Project is blocked (409 `QA_PROJECT_REQUIRED`). Requirement edits after a sign-off are informational (`requirementsChanged`) and never change the gate; a lead may reopen.
6. **The schema change is additive and applied before the backend.** The new code reads columns the old code does not know, so the migration goes first; it is idempotent and is re-run once after the deploy to catch checklists shared in between. The old per-workspace name index is replaced by one scoped to (workspace, Project, kind), and the earlier migration that created it is guarded so replaying the tree cannot recreate it. A checklist shared to repositories in two Projects becomes one requirement per Project (the original keeps its id so old runs stay linked).
7. **Cross-context access goes through ports.** `ProjectLinkPort` gains `getDeliveryProject` and `listDeliveryProjectsForGroup`; the frontend-repository rule for notifications reads the runtime-owned `DEPLOYMENT_TARGETS_QUERY`; deleting a Project removes its requirements through the new `DELIVERY_PROJECT_DATA_CLEANUP` port. The only inline `hierarchy.*` SQL is the one-time backfill, recorded as two exact pairs in the schema-ownership gate.
8. **A Developer needs a Feature before creating a repository (amendment, 2026-10-02).** Product owners write at least one active Feature in a Project (a `functional` requirement, not archived, owned by that Project) before a Developer (`app_role` `member`) can create a repository in it: `409 PROJECT_FEATURES_REQUIRED` with `deliveryProjectId`. One Feature unlocks it; User stories are not required. The rule is the allow-list `repositoryCreateRequiresFeature` (member only); admins are exempt and lead/qa are already refused (`REPOSITORY_CREATE_FORBIDDEN`). It is enforced in `WorkspaceGateService.assertCanCreateRepositories` (every create-wizard shape and `POST /projects/setup`) and in `RepositoriesService.createRepository` (`POST /delivery-projects/:id/repositories`), always before the first GitHub call and always AFTER the Project's existence, team and availability checks, so the 409 never reveals whether another team's Project has Features. Callers that run after the repository exists skip the re-check so a Feature archived mid-provisioning cannot strand it. It is skipped when `projects.qa-checklists` is off, since nobody can write Features then. Archiving the last Feature later does not touch existing repositories; it only blocks new ones. Identity-access reaches the count through the kernel port `PROJECT_REQUIREMENTS_READINESS` (implemented in projects), and `GET /groups/:groupId/project-folders` returns `featureCount` per folder from one batched query so the UI can explain the block.
9. **Requirements can be created in a batch (amendment, 2026-10-02).** `POST /delivery-projects/:id/requirements/batch` takes `{ kind, requirements: [{ name, description?, items? }] }` (1 to 20), has the same permission, capability guard and 404 as the single create, and writes all of them in one transaction. A duplicate name inside the batch (trimmed, case-insensitive) is `400 REQUIREMENT_BATCH_DUPLICATE_NAME` at the second occurrence; a collision with an existing active requirement of the same kind is `409 REQUIREMENT_NAME_TAKEN`, both with the 0-based `index`.

10. **QA writes test cases under a User story (amendment, 2026-10-19).** A User story (an item of a `functional` requirement) can hold test case categories (`projects.qa_test_case_categories`, a name unique per story, case-insensitive), each holding test cases (`projects.qa_test_cases`: a title and an optional expected result). Only QA and admins write them (`canManageTestCases`: qa, admin; others `403 TEST_CASE_MANAGE_FORBIDDEN`), because the QA Team owns how a story is tested; Product owners keep writing the stories. System requirement items take none (`409 TEST_CASES_STORY_ONLY`); an archived Feature or a delivered Iteration refuses the write like every other requirement write. Like Progress, the definitions persist across runs; like Verification, each result belongs to one run: `projects.qa_run_test_cases` holds each run's copy of a story's test cases with QA's result (`pending`, `passed`, `failed`, `blocked`, `not_applicable`), set on the Verification track (qa, lead, admin). An open run's copies follow the definitions: every definition write, a new run and `appendMissingItemsToOpenRuns` re-sync the Iteration's open runs in the same transaction (new test cases join as pending, edits keep their result, deleted ones leave). A signed-off run keeps its copies. A story cannot be `passed` while any of its test cases is `pending`, `failed` or `blocked` (`409 QA_TEST_CASES_OPEN`, checked under the run item lock), and an `APPROVED` sign-off is refused while any test case of the run is (same code), because a test case can be added or re-marked after its story passed. Lock order stays run, then run item, then test case; a test case write bumps its run item's `row_version`, so the sign-off's item fingerprint refuses a sign-off that raced one. The gate is unchanged: it already needs every story passed.

11. **Verification is Pending, Passed or Failed, and Failed returns the story to development (amendment, 2026-10-19).** QA sets a Project run item to `pending`, `passed` or `failed` only; `blocked`, `returned_to_dev` and `in_progress` answer `400 QA_VERIFICATION_STATUS_INVALID`. `failed` now does what `returned_to_dev` did: in the same transaction it puts the source item's Progress back to `in_progress` and clears the previous fix request, the story lands in the Developers' "returned" bucket of My QA items, the notification (`qa.item.failed`, owner, leads and developers) says it was failed and returned, and a Developer setting Progress to `done` re-queues it to `pending`. A severity is still required. Test case results are `pending`, `passed` or `failed` (`blocked` and `not_applicable` answer 400); a story passes once every test case is passed. Rows written before keep `blocked`, `returned_to_dev` and `not_applicable` and are read as before (open defects, returned, resolved), so no migration is needed.

12. **The Product owner accepts the signed-off run, item by item (amendment, 2026-10-20).** After QA signs a Project run off as `APPROVED` or `CONDITIONAL`, a Product owner or admin (`canAcceptRunItems`: lead, admin) checks each item with `PATCH /delivery-projects/:id/qa-runs/:runId/items/:itemId/acceptance` (`{ decision, expectedRowVersion, notes?, defectSeverity? }`). `passed` sets `qa_run_items.po_status` to `passed` with who and when (migration `20261021010000_qa_po_acceptance.sql`, additive). `failed` needs notes and reopens the run (the sign-off is superseded, as on Reopen), then sets the item `failed` with the notes prefixed "Product owner:" and the severity given (default `major`), which returns the story to the Developers as in amendment 11; QA re-checks it once a Developer marks it Done, and signs off again. The QA Team, the run's starter and signer, the repository owner, the workspace leads and the Developers are notified (`qa.item.po_rejected`), never the Product owner who failed it. Any QA status write resets the item's acceptance. The merge-to-main gate now also needs every item of the latest signed-off run accepted ("N items are waiting for the Product owner to pass them"). A run payload carries each item's `poAcceptance` and `permissions.canAccept`. Test case results become the QA Team's alone (`canRecordTestCaseResults`: qa, admin; others `403 TEST_CASE_RESULT_FORBIDDEN`, surfaced as `permissions.canRecordTestCases`): the Product owner reads them. QA's sign-off already notifies the Product owners (`qa.run.signed_off`, leads and owner).

## Consequences

- Persona rules are allow-lists in `qa-run-access.rules.ts`; `personaAllowsRole` and per-item `targetPersona` no longer gate anything.
- The old routes are kept for one release as deprecated: legacy checklist writes on a Project-owned row answer 409 `REQUIREMENT_MOVED_TO_PROJECT` (the item replace would delete Progress), and the per-repository feeds are derived from the repository's Project.
- A Project run notifies through the Project's frontend repository, else its oldest linked repository.
- Strict staleness is intended: the QA'd combination changed, so the sign-off no longer describes what would ship.
