# Changelog

## [Unreleased]

### Added

- Added Iterations phase 3, Start the next iteration (ITERATIONS_PLAN.md D2, D5, P2, P13): `POST /delivery-projects/:id/iterations` (lead and admin; non-members get 404, other roles 403 `ITERATION_START_FORBIDDEN`) with body `{ goal?, carryOver: { requirementItemIds } }`. It is allowed only when the Project's latest Iteration is delivered, otherwise `409 ITERATION_ACTIVE` ("Iteration N is still active. Deliver it before starting the next one."); a double click or a race hits the one-active partial unique index (or the `(project, number)` key) and the loser gets the same 409. Every carried id must be an item of an active requirement of the Project's latest delivered Iteration, otherwise `400 ITERATION_CARRY_INVALID` with `invalidIds` (all or nothing); a goal over 120 characters is `400 ITERATION_GOAL_INVALID`, an empty goal is stored as null. Iteration N+1 and the copy are created in ONE transaction: each source requirement with a selected item becomes a NEW requirement of the new Iteration (same workspace, kind, name, description, creator), carrying ONLY the selected items as NEW rows (order kept and renumbered, title, acceptance criteria, verification type, test identifier). An item whose status in the delivering run (`signoff_run_id`) was `failed`, `blocked` or `returned_to_dev` goes back to Progress `in_progress` (no progress author); every other item keeps its Progress, author and time. Delivered rows are never written. A start with nothing carried over is allowed. Records the audit event `qa.iteration.started` (`deliveryProjectId`, `iterationId`, `number`, `carriedItems`, `carriedRequirements`) and notifies the workspace Developers, leads and QA except the actor (`Iteration N+1 of <Project> started`, naming the goal and the carried count). Response `201 { iteration, carriedRequirements, carriedItems }`. `GET /delivery-projects/:id/iterations/current` gains `carryOver { fromIterationNumber, requirements: [{ requirementId, name, kind, items: [{ id, title, progress, lastStatus, suggested }] }] }`, only when `canStartNext` is true; `suggested` is unfinished (Progress not `done`, or not `passed` in the delivering run, or not in it). No migration: the phase 1 indexes already allow the same requirement names in a new Iteration and a new run on unchanged heads.
- Added Iterations phase 2, Delivered (ITERATIONS_PLAN.md): an Iteration becomes Delivered automatically, in one atomic `UPDATE ... WHERE status = 'active'`, when every repository the signed-off run covered has reached `main`, either by a Merge to main (`how: 'merged'`, with `mergeSha` and `prNumber`) or because `main` already contains the signed-off uat head (`how: 'already_in_main'`, found with `compare/{head}...main`: `ahead` or `identical`). The state is stored incrementally in `project_iterations.delivery_json` (`{ repositories: [...] }`), so a reload shows what is already merged. Only the caller whose update changes the row records the audit event `qa.iteration.delivered` and notifies the workspace leads, Developers and QA (`Iteration N of <Project> was delivered`). Added `POST /delivery-projects/:id/promotion/merge-all` (lead and admin): merges each covered repository in a stable order, keeps going after a failure, and a retry merges only what remains (`409 ITERATION_DELIVERED`, `QA_PROMOTION_BLOCKED`, `PROJECT_HAS_NO_REPOSITORIES`). `POST /projects/:id/qa/promotion/merge` answers `merged:false` with "main already contains this commit" instead of GitHub's refusal, records the delivery, and refuses a delivered Iteration with `409 ITERATION_DELIVERED`. `GET /delivery-projects/:id/iterations/current` gains `coveredRepositories` and `canMergeAll`, and `deliveredRepositories` is filled while active; `GET /projects/:id/qa/promotion` gains `repositoryDelivered`, `iterationDelivered`, `iteration` and `reasonCodes`; the team overview reads `promotion` from the stored state and adds `iteration` per Project. No migration.
- Added pull-request-only branch protection (ADR-0015): `dev`, `uat` and `main` now require a pull request (zero approvals, force push and deletion blocked, `enforce_admins` off for new rules), merged into any existing protection instead of overwriting it. It is applied at the end of every provisioning flow (best effort; audit events `project_branch_protection_applied` / `project_branch_protection_failed`) and retrofitted by the admin-only `POST /projects/:id/branch-protection` and `POST /admin/branch-protection/apply`, which return per-branch `applied`, `unchanged`, `missing` or `failed`. The `branch_dev_protected` drift finding is gone; a `dev` that accepts direct pushes is now `branch_protection_missing`.
- Added `GET /projects/:id/commits?branch&limit&before`: the commit history of a branch (`{ branch, branches, items, next }`), with the pull request number read from the message, the caller's OAuth token first and the installation token as fallback, and the sign-in-again error for a revoked session token.
- GitHub activity in the repository Audit trail: pushes, pull requests, reviews, and branch and tag creation or deletion are polled from the GitHub Events API (webhooks do not reach the backend) into `audit.audit_events` with scope `github`, at most once a minute per repository, on the first page of `GET /projects/:id/audit`, which gains `githubSync` (`ok`, `stale`, `failed`). `POST /projects/:id/audit/sync` forces a sync. Migration `20261002020000_audit_github_activity.sql` adds a unique `audit.audit_events.external_id` and `audit.github_event_syncs`; apply it with `npm run db:apply` before the backend deploys.
- Repository Audit works for the whole team: `GET /projects/:id/audit` no longer filters on the repository's creator, so Product owners, QA, other Developers and admins who can see the repository see its events (404 otherwise). The response gains `actorLogin`, `metadata`, `scope` (`repository` or `project`) and a `next` cursor; `?limit` (default 50, max 100) and `?before=<ISO createdAt>` page it. Project-level requirement and checklist events (written with no repository) now appear on every repository of their Project. Recording is still gated by `AUDIT_EVENTS_ENABLED`.
- Added migration `20261002010000_backfill_dropped_audit_events.sql` (platform-ops): copies the `platform.audit.recorded` outbox events that were dropped while recording was off into `audit.audit_events`, deduped by a new unique `outbox_event_id`; deleted repositories keep their event with `project_id` NULL. Apply with `npm run db:apply`; rollback in `supabase/rollbacks`.
- Added the Feature-before-repository rule (ADR-0014, decision 8): a Developer (`app_role` `member`) can create a repository in a Project only after a Product owner wrote at least one active Feature (`kind='functional'`, not archived) in it; otherwise `409 PROJECT_FEATURES_REQUIRED` with `deliveryProjectId`, before any GitHub call. It covers `POST /projects`, `POST /projects/setup` and `POST /delivery-projects/:id/repositories`. Admins are exempt, the rule is skipped when `projects.qa-checklists` is off, and archiving the last Feature later only blocks new repositories. New kernel port `PROJECT_REQUIREMENTS_READINESS` (projects owns the read) and `GET /groups/:groupId/project-folders` now returns `featureCount` on each folder (additive). No migration.
- Added `POST /delivery-projects/:id/requirements/batch`: creates 1 to 20 requirements of one kind in a single transaction (`201 { requirements }` in request order), with `REQUIREMENT_BATCH_INVALID`, `REQUIREMENT_BATCH_DUPLICATE_NAME` and `REQUIREMENT_NAME_TAKEN` (each carrying the offending `index`) refusals.
- Added Project requirements (ADR-0014): requirements belong to a Project (`functional` Features with User stories, `system` checklists), developers report Progress (`todo`/`in_progress`/`done`) while QA verifies once per Project through Project-scope runs that capture every repository's `uat` head, and Merge to main is gated on the Project's latest signed-off run being Approved and current for every repository. New routes under `/delivery-projects/:id/requirements`, `/requirements/:id`, `/delivery-projects/:id/qa-runs`, `/delivery-projects/:id/qa/my-items` and `/workspaces/:id/qa-requirements/overview`; the repository-scope run routes are read-only history (`QA_RUN_LEGACY_READONLY`) and the old checklist routes are deprecated. The migration `20261001010000_project_requirements.sql` is additive and must be applied before the backend deploys, then re-run once after.
- Added ADR-0013 (QA verification runs): the `qa` persona derived from the `qa-team` GitHub team, workspace checklists shared to projects, runs keyed on project, checklist, branch and server-resolved commit with snapshotted items, persona-based item rights, server-enforced sign-off with a frozen `report_json`, run-row locking against concurrent edits, the `qa-report/v1` JSON and Markdown export, and automated CI results shown beside manual verdicts without changing them.
- Added proposed ADR-0012 (configurable deployment targets) and a consolidated on-premises setup plan. Customer projects can choose a provider per slot and branch: the first planned mix uses Vercel/Render for `dev` (test) and `uat`, then customer-hosted `onprem-compose` for `main`. AlphaCI platform hosting stays managed in this delivery; `onprem-k8s` and self-managed platform hosting are later options. The plan replaces the Kubernetes-only on-premises report and diagram.

Added `GET .../logs/stream?mode=append` for an SSE live tail that sends one snapshot then only new lines per poll, capped at 5 provider pages per tick.

### Changed

- A new Iteration now always starts empty (ITERATIONS_PLAN.md 6a, replaces D2's carry-over): every item must be passed before Merge to main, so a delivered Iteration holds no unfinished work and nothing is carried. `POST /delivery-projects/:id/iterations` answers `201 { iteration }` (no `carriedRequirements` / `carriedItems`), still accepts an absent or empty `carryOver.requirementItemIds`, and refuses a non-empty one with `400 ITERATION_CARRY_INVALID` (`invalidIds`). `GET /delivery-projects/:id/iterations/current` no longer sends `carryOver`. The delivered Iteration's requirements stay frozen with it. The `qa.iteration.started` audit metadata drops the carried counts and the notification says the iteration starts with an empty checklist. No migration.
- Developers (`app_role` `member`) and admins now manage hosting (deployment targets, custom domains) and environment variables; Product owners (`lead`) lose those edit rights, QA is unchanged. The `HOSTING_LEAD_ONLY` and `ENV_VARS_LEAD_ONLY` codes are kept for the deployed frontend with role-neutral messages, and an unresolved role is now refused instead of defaulting to a persona. Reinstalling deployment secrets follows the hosting rule (admin and Developer); provider connections, disconnecting a project and drift repair stay admin and lead.
- Classified optional provider and live-adapter mode toggles as explicit non-capability flags so the resolver gates base capabilities only on their primary enablement flags.
- Changed `/api/v1/capabilities` to project its resolved deployment set into the existing compatibility fields and expose top-level `edition` and `capabilityKeys`, preserving the legacy nested response for the default fixture.
- Changed the deployment-targets, provider-connections, env-vars, and custom-domains controllers to enforce `runtime.env-provisioning` through `CapabilityGuard` before `SubscriptionGuard`; removed the obsolete `EnvFeatureGuard`.
- Moved capability catalog authority into the application kernel and declared edition applicability through manifests; PR 1 adds a behavior-neutral pure resolver without changing a request endpoint or build artifact.
- Made the SaaS, EDU, and Enterprise pack profiles list every shared capability in registry order, with status derived from the capability registry rather than sampled per pack.
- Recorded that the frontend repository keeps a matching current-state Golden Copy bundle that snapshots this catalog.
- Recorded SaaS, EDU, and Enterprise target gaps as `not-implemented` capability keys, and added pack status `not-applicable` for keys outside a pack.
- Extended `check:capabilities` to reject pack tables that omit, reorder, or restate capability status outside the shared catalog rule, and to forbid AppConfig flags on `not-implemented` records.
- Replaced obsolete architecture and operational document locations with current lower-kebab canonical paths.
- Synchronized the npm lockfile with the existing `js-yaml` dependency so clean `npm ci` installation succeeds.
- Kept the existing HTTP route inventory, public DTO compatibility, and product workflow behavior while tightening internal delivery and composition boundaries.
- Composed Runtime provider contributions through validated provider packs, retaining the current Render, Vercel, and GCP registrations and compatibility fields.
- Changed the PostgreSQL outbox relay to claim rows with short leases, release the database transaction before handler I/O, and acknowledge only the matching claim.
- Made hierarchy member offboarding and revoke-event publication share one transaction, so a failed enqueue rolls back the member and assignment changes together.
- Made the scheduled hierarchy relay require an explicit `live` or `stub` mode instead of relying on an implicit deployment default.
- Updated the outbox reliability migration, topic quarantine migration, and rollback procedures to document the active schema and recovery behavior.
- Linked ADR-0002 and ADR-0003 forward to the composition decisions instead of rewriting their original narrowing statements.
- Moved the SaaS-to-Enterprise review out of the canonical documentation bundle, and made the bundle gate skip the `superpowers` directory.

### Fixed

- Recover unsigned on-prem deployments after signing failure without accepting late signatures or allowing CI to overwrite signed host results. Replacing a host now revokes previous tokens for only that environment, with concurrent registrations serialized and one active token enforced by migration. Rollback rechecks a configured application HTTP health URL before reporting success. Added the host setup runbook and documented the migration, workflow regeneration, and agent update required for rollout.
- Fixed the architecture route-inventory check failing on Windows checkouts by pinning `*.txt` to LF, so the committed baseline hash matches the working tree.
- Corrected outbox acknowledgement to update the active `published_at` column rather than the removed legacy `processed_at` column.
- Added fail-closed protection to the branch-scoped environment rollback so it cannot silently discard preview branch identity in the legacy schema.
- Preserved hierarchy failure context when GitHub repository or user resolution fails, allowing retry and audit handling to retain the group and acting-user context.
