# Changelog

## [Unreleased]

- QA Verification is Pending, Passed or Failed (ADR-0014, amendment 11). Failed always sends the story back to the Developers: its Progress returns to In progress in the same write, it shows in their "returned" My QA items, the notification says it was failed and returned, and marking it Done re-queues it for QA. Blocked and Returned to dev are no longer accepted on a Project run (`400 QA_VERIFICATION_STATUS_INVALID`), and test case results are Pending, Passed or Failed. Existing rows keep their status. No migration.
- Workspace member additions now enqueue a durable recipient notification in the membership transaction. Authenticated live notification snapshots keep the Inbox and badge current, with deduplicated delivery, explicit workspace links, and a notification-only one-second relay.

### Added

- Two-repository projects with their own environments, including on-prem hosting. `POST /projects` with `repoShape: multi-repo` now accepts `environments` (with an optional `hostAssignment` each) and per-environment `backend` and `frontend` targets. Before, it was refused with 400. Each repository is its own project row and gets the environment pipeline that a single-repository project gets, limited to its own slot: the backend repository gets the `backend` targets and the frontend repository the `frontend` targets. Each one has its own environment branches, release signing (`ALPHACI_RELEASE_SIGNER=runner|file`), generated release pipeline, releases and promotions. The halves are cross-linked per environment, and both rows are filed under the same delivery project, as every pair is. Host assignment after creation runs for both rows. Each row is assigned only its own slot's port and health entries with the shared ingress, and host ports are allocated per machine, so the two rows cannot collide. The response adds `secondaryProjectId` (the frontend row), `secondaryRepoError` (when the frontend repository failed and was removed; the backend repository is kept), and `projectId` and `slot` on each `hostAssignments` entry of a pair. A `standalone` target is refused for this shape. Microservices projects still refuse `environments`. Hosted pairs created without `environments` are unchanged. The environment pipeline steps now live in one module (`environment-project.pipeline.ts`) used by both shapes. No migration.
- On-prem: the backend and frontend of a two-repository project run linked on one machine. When the backend project and the frontend project, filed under one delivery project, both have an environment with the same slug assigned to the same machine, `GET /onprem/assignments` adds `assignment.link` to those environments' deployments: `network` (`alphaci-<pair>-<slug>`), per-slot `env` (frontend `API_URL=http://backend:<backend container port>`; backend `FRONTEND_URL` and `CORS_ORIGINS` once the frontend has a tunnel or configured address) and `peers` (the other half). The link is derived on every read and never stored, and sits outside the signed envelope. A single app, a missing half, a half on another machine, a different slug or an ambiguous Project gets no link and exactly the previous payload. Agent 0.4.0 validates the link (network name, slots, `^[A-Z_][A-Z0-9_]*$` variable names, values without control characters; an invalid link fails the deployment before anything changes), creates the network, joins each container under its slot alias, writes the variables into Compose with `$` escaped, and attaches the other half's running container. The link is sent only to machines whose last heartbeat reported agent 0.4.0 or newer; older agents get exactly the previous payload and deploy unlinked. Readiness adds a `service-link` check for linked environments that fails on agents older than 0.4.0. The agent version is 0.4.0 (heartbeat, enrollment, installer manifest). No migration.
- QA test cases under a User story (ADR-0014, amendment 10). The QA Team (role `qa`) and admins add test case categories to a story of a Feature and test cases inside them (title, optional expected result): `POST/PATCH/DELETE /requirements/:id/items/:itemId/test-categories[/:categoryId]`, `POST .../test-categories/:categoryId/test-cases`, `PATCH/DELETE .../test-cases/:testCaseId`. Every write answers the story's whole set and re-syncs the Iteration's open QA runs in the same transaction. In a Project run, QA records each test case as Pending, Passed, Failed, Blocked or Not applicable with `PATCH /delivery-projects/:dpId/qa-runs/:runId/items/:itemId/test-cases/:testCaseId` (qa, lead, admin). A story cannot be marked Passed, and a run cannot be signed off APPROVED, while a test case is pending, failed or blocked (`409 QA_TEST_CASES_OPEN`). Requirement items and run items carry `testCategories`; the requirement list and run permissions carry `canManageTestCases`; the QA report lists the test cases (Markdown table per story, Excel "Test cases" sheet). Migration `20261020010000_qa_test_cases.sql` (three new tables, additive; rollback in `supabase/rollbacks`): apply it before the backend that uses it deploys.
- Vercel deploy history now includes production. It used to read only the newest 20 deployments across every branch, and on a busy project those are all dev/uat previews, so production had no history: an empty Production list and nothing to roll back to. The client now also reads the latest 10 production deployments and merges them in, each once, newest first. If that extra read fails, the history is returned as before.
- Roll back a deployment from inside ALPHACI. `POST /projects/:projectId/deployment-targets/:targetId/rollback` with `{ deployId, reason }` puts an earlier deploy back live: Render's rollback API redeploys that deploy's build as a new "rollback" deploy, and Vercel's Instant Rollback points the production domains at that deployment. Developers and admins only (`canManageHosting`), the same bar as every other hosting action. The deploy must be among the service's recent deploys, have gone live, not be live now, and on Vercel be a production deployment. A reason is required. Each rollback is recorded in the Audit trail (`deployment_target_rolled_back`) with who did it, the commit and the reason. Vercel holds new production deploys off the domains after a rollback, so the hold is kept on the target's `providerMetadata.rollback`, and `POST …/rollback/resume` promotes the newest ready production deployment and clears it (`deployment_target_rollback_resumed`). The target actions descriptor gains `rollback: { enabled, resumable }`. No provider dashboard is involved.
- The self-hosted appliance has an optional on-prem block in `deploy/selfhost/alphaci.env.example`: `ONPREM_RELEASES_ENABLED`, `ENV_PROVISIONING_ENABLED` and the installer source, all commented out. `alphaci-ctl doctor` adds two checks while `ONPREM_RELEASES_ENABLED=true`: the on-prem settings (names each missing or malformed one) and the release trust key for on-prem hosts (prints the key ID enrollment trusts). Both checks print nothing while on-prem is off.
- Self-hosted appliance (phase 1): `deploy/selfhost/` runs the API, migration runner, frontend and Postgres 16 on one server behind a Caddy edge (one HTTPS origin, `/api/*` to the API). Secrets are files under `secrets/` read through an allow-listed `*_FILE` loader (`src/kernel/config/file-env.ts`). `alphaci-ctl` (`init`, `admin-grant`, `doctor`) is compiled into the image as `dist/src/cli/alphaci-ctl.js`. The API image now listens on `PORT` (default 4000) with a health probe on `/api/v1/health`, and carries `supabase/migrations/` and the role bootstrap. Runbook: `docs/runbooks/runbook-selfhost-install.md`. SaaS builds are unchanged.

- Added `ALPHACI_RELEASE_SIGNER=file` for self-hosted AlphaCI: the backend signs release manifests with a customer-held P-256 key (`ALPHACI_RELEASE_SIGNING_KEY_FILE`) right after registration, so no signing job or signing secret reaches GitHub. The derived public key joins the trust set and new host enrollments. Runner signing (the default) is unchanged.
- Self-hosted migration runner (`npm run db:migrate:selfhost`, compiled as `dist/src/scripts/migrate-selfhost.js`) applies the Supabase migration tree to a plain PostgreSQL 16 database. It takes an advisory lock, bootstraps the Supabase-compatible `anon` and `authenticated` roles from `deploy/selfhost/postgres-init/00-roles.sql`, records each migration in `public.schema_migrations` with a checksum, and refuses to start when an applied file has changed. The QA attachment migration skips its `storage.buckets` insert when Supabase Storage is absent. SaaS migration tooling is unchanged. No migration.

- Self-hosted runtime without Supabase (WP-A). `ALPHACI_DEPLOYMENT_MODE=saas|selfhosted` (default `saas`, unchanged) selects the self-hosted rules: `SESSION_STORE_DRIVER=postgres` is required, `DATABASE_URL` is required, `PLATFORM_PUBLIC_URL` is required, and `STORAGE_DRIVER=supabase` is rejected. `STORAGE_DRIVER=postgres|supabase` selects where QA screenshot bytes live. Unset, it is `supabase` when `SUPABASE_URL` or `SUPABASE_SERVICE_ROLE_KEY` is present (SaaS, unchanged) and `postgres` otherwise. The postgres driver stores bytes in the new `projects.qa_attachment_objects` table (migration `20261019010000_qa_attachment_objects.sql`, rollback in `supabase/rollbacks`, 3 MB cap) and serves them through `GET /api/v1/qa-attachments/content` behind five-minute HMAC links. The health database check is a `SELECT 1` through the app's pool instead of a Supabase Auth call. `DATABASE_URL` is read ahead of `SUPABASE_DB_URL`. Every `SUPABASE_*` variable is optional unless the Supabase storage driver is selected. The unused service-scoped Supabase clients (`<SERVICE>_SUPABASE_URL` pairs) are removed. Apply the migration with `npm run db:apply` before the backend that uses it deploys.
- QA screenshot content route throttle and cache validation. `GET /api/v1/qa-attachments/content` (self-hosted, `STORAGE_DRIVER=postgres`) has its own limit of 300 requests a minute per client address, replacing the 60 a minute app default for this route only, because a QA run page loads one request per screenshot. Responses carry an `ETag` (SHA-256 of the stored bytes) and answer `304 Not Modified` to a matching `If-None-Match`. `Cache-Control: private, max-age=300` is unchanged.
- Orphaned QA screenshot bytes are swept. Deleting a run or project removes its attachment rows but not the bytes in `projects.qa_attachment_objects`. With `STORAGE_DRIVER=postgres` a worker deletes objects older than one hour that no attachment row references, 500 at a time, every 15 minutes (up to 10 batches per tick). A transaction-scoped advisory lock lets only one api replica sweep at a time. Migration `20261019020000_qa_attachment_objects_created_at_index.sql` (rollback in `supabase/rollbacks`) adds the index that serves the oldest-first scan; the sweep runs without it, only more slowly.
- Render deploys read the way Render shows them. A Render image deploy carries its commit only in the image tag, so `GET /projects/:id/deployments` and `GET /projects/:id/previews` now read it from `sha-<commit>`; they also return `trigger` and `startedAt`, and Render's `deactivated` (replaced by a newer deploy) is the new status `superseded` instead of `unknown`. Render's pre-deploy and update states map to building or failed. Each branch preview gains `recentDeploys` (its newest five, current first), and a deploy the provider sent no message for gets its commit's first line from one cached read of the branch's recent commits (installation token, 60 s per branch).
- Generated workflows run once per commit. While a pull request whose head is a pipeline branch (dev, uat, main) is open, a push to that branch started two chains for the same commit, and both released it: every uat commit was deployed to Render twice. A chained stage now skips a run started by such a pull request (`workflow_run.event == 'pull_request'` and `pull_requests[0].head.ref` is a pipeline branch), the way it already skips a fork's run; the push chain covers that commit and the pull request's status. Feature-branch pull requests still run. Existing repositories pick this up through the Pipeline settings workflow-update pull request.
- `GET /projects/:id/workspace/files/commits?path&ref`: the Code tab's commit column. For the listed folder (or file) it returns `latest`, the most recent commit under that path (sha, short sha, first line of the message, date, author login, name and avatar), `totalCommits` (the branch's total at the root), and `entries`, the latest commit of each entry keyed by path. It costs one GraphQL request per 50 entries (`history(first: 1, path: …)` per entry under an alias, paths passed as variables) instead of one REST call per file, and entries past 300 come back null. The entries are re-read from GitHub server-side, not accepted from the browser. Asked for once per opened folder or file, after its listing, and never polled. New `GithubProjectPort.listPathCommits`. No migration.
- `GET /projects/:id/workspace/browser-tests` gains `ownTests { count, paths }`: the repository's own Playwright test files on dev (any name under an `e2e`/`playwright` folder or named `*.e2e*`, in a repository that uses Playwright), which the verify stage already runs. Before, a repository with its own suite read as having no browser tests because only the starter pack's file names were checked. Read from GitHub's recursive tree (new `GithubProjectPort.listRepoPaths`) for the status only; the add flow is unchanged. Null without a dev branch.

### Changed

- The self-hosted install runbook documents how to switch an existing on-prem host to the install's signing key: when to do it, the re-enroll path for the Ubuntu script, the `.deb` package, WSL and the Windows installer, the manual `trust.json` entry, and how to verify the switch. The on-prem host setup runbook's move procedure now matches `enroll.sh`, which accepts `--replace` for an address change.
- Generated pipelines use the Project's one coverage threshold on dev, uat and main. The Quality stage used to add 10 points on uat and main (capped at 95), so a commit at 85% passed dev at the default 80 and then failed the same code on uat at 90. Every branch now uses the threshold chosen for the Project (80 by default). uat and main stay strict in the other ways: warnings fail and the SonarCloud gate is awaited. `promotion-coverage-threshold` is still published, equal to the gate, so the central test workflows' "would fail uat" warning simply never fires. Existing repositories pick this up through the workflow update pull request; because stages 2 to 4 run from the default branch's copy of the workflow (`workflow_run`), the new threshold applies once that update reaches `main`.
- Merge to main now needs every requirement item of the Iteration passed (ITERATIONS_PLAN.md, revised Phase 3): a run snapshots its items when it starts, so a story added later was never verified, and a requirement changed after the sign-off was only a note. An Approved sign-off of a Project run is refused with `409 QA_RUN_MISSING_ITEMS` (`missingItems`) when the Iteration holds an active item the run did not pass (those items are added to the run as pending, so QA verifies them and signs off again), and the Project merge gate (single-repository merge, `merge-all` and `canMergeAll`) is closed with a reason when the signed-off run did not pass every active item or when a requirement changed after the sign-off (`requirementsChanged` is now blocking, not a note). ### Fixed

- QA Studio can show uat (and every other preview) of an ALPHACI-managed Vercel frontend again. ALPHACI created Vercel projects with Vercel's default Standard Protection, which puts every preview deployment behind a Vercel sign-in (a redirect to `vercel.com/sso-api`), and uat always deploys as a preview. QA Studio then said "This deployment is behind deployment protection", and a QA tester without a seat on ALPHACI's Vercel team could not open it in a new tab either. Installing a managed Vercel target's CI secrets (at provisioning, and again on **Reinstall deployment secrets**) now turns off Vercel Authentication (`ssoProtection: null`) on that project, so its previews are public. Only Vercel Authentication is cleared: password protection, trusted IPs and the automation bypass secrets stay. A project connected with the customer's own Vercel account is not touched. Best effort: a refusal logs a warning and the secrets still install. An existing project picks it up through **Reinstall deployment secrets** on its Vercel target where project target management is enabled; otherwise turn off Vercel Authentication under the Vercel project's Settings > Deployment Protection. No migration.
- Project member GitHub access is granted again. `SESSION_USER_LOOKUP` was aliased to `UsersRepository`, which had `findById` but not the contract's `findSessionUser`, so every grant and revoke job threw `findSessionUser is not a function` and was quarantined after 5 attempts, leaving the assignment `pending` (which **Re-sync GitHub access** treats as live and skips). `UsersRepository` now `implements SessionUserLookup`, so the compiler enforces the contract, and a new spec compiles the real `AuthIdentityModule` and resolves the token. A repository or user lookup that throws during a grant or revoke now goes through the existing failure path (grant `failed`, revoke stays `revoking`, bounded requeue), so Re-sync and adding the member again can recover it. The "no write access" refusal on a merge, pull request or commit now tells a Developer to ask their Product owner to add them to the Project as a Developer. No migration; the two events already quarantined in production have to be re-queued once after deploy.
- Security: generated workflows no longer run a stage chained off another repository's code. A pull request from a fork runs the fork's own `00-alphaci-access.yml`, and `workflow_run` then started Quality, Package and Verify here with this repository's secrets, trusting the fork run's `alphaci-pipeline-context` artifact (or its `head_branch` / `head_sha`), so a fork could get its commit built, pushed and deployed as `uat`. The `pipeline-context` job, which every other job of a chained stage needs, now runs only when `github.event.workflow_run.head_repository.full_name == github.repository`, and the `always()` `report-results` job carries the same condition, so the whole stage skips. Write scopes moved from the workflow level to the jobs that use them (SonarCloud githubactions:S8233): Quality is read-only (its `security-events: write` was unused), Package drops `packages: write` (the image builds already grant themselves `packages` and `security-events`), and the env guard's `contents` / `issues: write` sit on its one job. Existing repositories get the fix through the workflow update pull request.
- The CI results export shows SonarCloud percentages with one decimal, as SonarCloud does: coverage on new code arrives unrounded (`96.27659574468085`) and is now `96.3%`. Values SonarCloud already rounded are unchanged.
- Recover unsigned on-prem deployments after signing failure without accepting late signatures or allowing CI to overwrite signed host results. Replacing a host now revokes previous tokens for only that environment, with concurrent registrations serialized and one active token enforced by migration. Rollback rechecks a configured application HTTP health URL before reporting success.
